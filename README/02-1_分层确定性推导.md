# 分层确定性推导：BIP32, 39, 44

## 核心问题：为什么需要这三个协议？

想象你是一家交易所，需要给 100 万用户生成钱包地址。

**最笨的办法：** 每个用户生成一个独立的私钥

- 100 万个私钥 = 100 万份备份
- 一个用户丢失 = 一笔资产无法恢复
- 管理成本 = 噩梦

**聪明的办法：** 用一个东西生成所有私钥

- 这就是 **BIP32 / BIP39 / BIP44** 要解决的问题

---

## 第一层：BIP32 - 分层确定性钱包（Hierarchical Deterministic）

### 问题

如何从**一个种子**推导出**无限多个私钥**？

### 解决方案

#### 核心概念：树形结构

```
一个种子（512 bits）
    ↓
[HMAC-SHA512 运算]
    ↓
主私钥 km + 主链编码
    ↓
    ├─ 子私钥 k0（索引 0）
    │  ├─ 孙私钥 k0/0
    │  ├─ 孙私钥 k0/1
    │  └─ 孙私钥 k0/2
    │
    ├─ 子私钥 k1（索引 1）
    │  ├─ 孙私钥 k1/0
    │  ├─ 孙私钥 k1/1
    │  └─ 孙私钥 k1/2
    │
    └─ 子私钥 k2（索引 2）
       ├─ 孙私钥 k2/0
       ├─ 孙私钥 k2/1
       └─ 孙私钥 k2/2
```

#### 推导过程（以 k0 为例）

```
父私钥 km (256 bits)
+
父链编码 (256 bits)
+
索引号 0 (32 bits)
    ↓
[HMAC-SHA512 运算] ← 这是关键！
    ↓
输出 512 bits → 分成两部分
    ├─ 左 256 bits → 子私钥 k0
    └─ 右 256 bits → 子链编码

然后用 k0 + 其链编码，就能继续派生孙私钥
```

### 推导的两种模式

| 模式         | 索引范围       | 特点         | 安全性   |
| ------------ | -------------- | ------------ | -------- |
| **常规派生** | 0 ～ 2^31-1    | 用父公钥推导 | 一般     |
| **强化派生** | 2^31 ～ 2^32-1 | 用父私钥推导 | **更强** |

**区别：** 强化派生用 `i'` 表示（带撇号），不能从父公钥推导，更安全。

### 关键性质

✅ **确定性：** 相同输入 = 相同输出（可重复推导）  
✅ **单向性：** 子密钥无法推出父密钥  
✅ **隔离性：** 兄弟密钥无法互相推导  
✅ **无限性：** 可以无限派生新的私钥

**比喻：** 就像从一粒种子长出一棵无限繁殖的树，每根枝条都是独立的，但都来自同一粒种子。

## 第二层：BIP39 - 助记词（Mnemonic）

### 问题

种子是 512 位的二进制数，用户怎么记？怎么安全备份？

```
种子长这样：0110101010001101010...（512个0和1）
用户看了：？？？什么玩意儿？
```

### 解决方案：用 12 个单词代替

```
助记词：candy maple cake sugar pudding cream honey rich
        smooth crumble sweet treat

vs

种子：5b56c417303faa3fcba7e57400e120a0c83ec5a4fc9f fba757fbe63fbd77a89
```

**哪个更容易记住和备份？** 显然是单词。

### 生成助记词的过程

参考图 3（助记词生成）：

```
第①步：生成随机数（128 bits）
  ↓
第②步：计算校验位（4 bits）← SHA256 的前 4 bits
  ↓
第③步：拼接 = 128 + 4 = 132 bits
  ↓
第④步：分成 12 段，每段 11 bits
  ↓
第⑤⑥步：每段 11 bits 对应一个数字（0-2047）
        查 BIP39 单词表中的第 i 个单词
  ↓
第⑥步：得到 12 个单词
```

**代码示例：**

```javascript
var bip39 = require("bip39");
var mnemonic = bip39.generateMnemonic();
// 输出：candy maple cake sugar pudding cream honey rich smooth crumble sweet treat
```

### 从助记词恢复种子

参考图 4（助记词到种子）：

```
助记词：
"army van defense carry jealous true garbage claim echo media make crunch"
+
盐值：
"mnemonic" + 可选密码（比如 "mypassword"）
    ↓
[PBKDF2 密钥拉伸函数]（使用 HMAC-SHA512）
    ↓
重复运算 2048 次 ← 增加破解难度
    ↓
得到 512 bits 的种子
    ↓
这个种子就可以用来派生私钥了！
```

### 密码的妙用

```
相同助记词 + 不同密码 = 完全不同的种子 = 完全不同的账户
```

**例子：**

```
助记词：candy maple cake sugar...
+ 密码："" (空)      → 生成种子 A → 账户 A
+ 密码："password1"  → 生成种子 B → 账户 B
+ 密码："password2"  → 生成种子 C → 账户 C
```

**安全性：** 即使黑客窃取了助记词，没有密码也无法恢复账户。

## 第三层：BIP44 - 标准化路径

### 问题

有了 BIP32 和 BIP39，我们能生成无限私钥。但问题是：

```
用户 A 用路径 m/0/0/0/0 生成第一个账户
用户 B 用路径 m/1/1/1/1 生成第一个账户

哪个对应比特币？哪个对应以太坊？
用户 A 的账户能否在另一个钱包软件中恢复？

乱套了！
```

### 解决方案：统一的路径规范

BIP44 定义了**5 层标准树状结构：**

```
m / purpose' / coin' / account' / change / address_index
↑     ↑        ↑        ↑         ↑          ↑
固定   固定    币种    账户     地址类型   地址编号
      44
```

### 各层详解

#### 第 1 层：purpose'（固定 44'）

```
m / 44' / ...
    ↑
    表示使用 BIP44 标准（44 是 BIP 的编号）
    必须是强化派生（有撇号）
```

#### 第 2 层：coin'（币种编码）

| 币种         | 编码    | 路径              |
| ------------ | ------- | ----------------- |
| 比特币       | 0'      | m/44'/0'/...      |
| 比特币测试网 | 1'      | m/44'/1'/...      |
| **以太坊**   | **60'** | **m/44'/60'/...** |
| Litecoin     | 2'      | m/44'/2'/...      |
| Solana       | 501'    | m/44'/501'/...    |

完整列表：https://github.com/satoshilabs/slips/blob/master/slip-0044.md

#### 第 3 层：account'（账户索引）

```
m/44'/60'/0' / ...  ← 账户 0
m/44'/60'/1' / ...  ← 账户 1
m/44'/60'/2' / ...  ← 账户 2
```

用户可以有多个账户，每个账户相互独立。

#### 第 4 层：change（地址类型）

```
m/44'/60'/0'/0 / ...  ← 0 = 外部链（收款地址）
m/44'/60'/0'/1 / ...  ← 1 = 内部链（找零地址）
```

- **0 = 收款地址**：公开给他人，用来接收转账
- **1 = 找零地址**：钱包内部使用，接收零钱

大多数情况只用 0。

#### 第 5 层：address_index（地址序号）

```
m/44'/60'/0'/0/0  ← 第 1 个地址
m/44'/60'/0'/0/1  ← 第 2 个地址
m/44'/60'/0'/0/2  ← 第 3 个地址
```

### 以太坊的完整示例

```
路径：m/44'/60'/0'/0/0

m           主私钥
 ↓
44'         BIP44 标准
 ↓
60'         以太坊
 ↓
0'          账户 0
 ↓
0           收款地址
 ↓
0           第 1 个地址
```

**生成的地址：**

```
私钥：0x1a2b3c4d5e6f7a8b9c0d1e2f3a4b5c6d7e8f9a0b1c2d3e4f5a6b7c8d9e0f1a
公钥：04a1b2c3d4e5f6...
地址：0x5aAeb6053ba3EFa8899CbEaF830d8fd7c054f90b ← 可以接收转账了！
```

## 完整流程：从助记词到可用地址

```
第 1 步：生成或导入助记词
"candy maple cake sugar pudding cream honey rich smooth crumble sweet treat"
    ↓ [BIP39]

第 2 步：助记词 + 密码 → 种子（512 bits）
"mnemonic" + "" (或你的密码)
使用 PBKDF2 拉伸 2048 次
    ↓ [PBKDF2 + HMAC-SHA512]

第 3 步：种子 → 主私钥 km
    ↓ [HMAC-SHA512]

第 4 步：主私钥按路径派生
m/44'/60'/0'/0/0
每一层都是 HMAC-SHA512 运算
    ↓ [BIP32]

第 5 步：得到最终私钥 k5
    ↓ [椭圆曲线]

第 6 步：私钥 → 公钥
    ↓ [Keccak256 哈希]

第 7 步：公钥 → 地址
    ↓ [EIP-55 校验和]

第 8 步：最终地址
0x5aAeb6053ba3EFa8899CbEaF830d8fd7c054f90b
```

## 为什么这三个协议必须一起用？

### BIP32 alone（只有 BIP32）

❌ 私钥生成没有统一标准  
❌ 不同应用用不同的派生路径  
❌ 账户之间容易混乱

### BIP32 + BIP44（加上 BIP44）

✅ 路径标准化，不同钱包能互相恢复账户  
✅ 支持多币种  
❌ 但用户怎么备份 512 位的种子？

### BIP32 + BIP39（加上 BIP39）

✅ 12 个单词容易记住  
❌ 但路径还是乱的，不同应用生成的地址不兼容

### BIP32 + BIP39 + BIP44（三个一起）

✅ **完整解决方案！**

- BIP39：助记词 + 种子生成
- BIP32：分层派生私钥
- BIP44：标准化路径

这就是现在所有主流钱包（MetaMask、Ledger、Trust Wallet 等）都遵循的标准。

## 交易所应用：签名机如何工作

```
用户注册
    ↓
交易所分配一个路径：m/44'/60'/0'/0/{n}
    ↓
签名机根据路径派生私钥
    ↓
生成对应的公钥 → 地址
    ↓
数据库保存：用户 ID、地址、路径（不保存私钥！）
    ↓
用户可以接收转账
    ↓
用户要提币时：
  1. 签名机查询数据库找到路径
  2. 根据路径重新派生私钥
  3. 用私钥签名交易
  4. 返回签名后的交易（不返回私钥！）
  5. 交易上链
```

## 关键安全原则

| 原则                      | 为什么                       |
| ------------------------- | ---------------------------- |
| 私钥永不落盘              | 避免被黑客读取               |
| 路径 + 密码可以重推导私钥 | 动态生成，无需存储           |
| 助记词离线冷备份          | 一旦泄露，黑客可恢复所有账户 |
| 密码足够复杂              | 防暴力破解                   |
| 签名机内网隔离            | 防外网直接攻击               |

## 常见问题

**Q: 为什么非要用强化派生（带撇号）？**  
A: 强化派生用父私钥计算，即使父公钥泄露也无法推导。常规派生可以从公钥直接推导，风险更高。

**Q: 忘记了密码怎么办？**  
A: 无法恢复。这就是为什么密码要记住或安全备份（不要和助记词放一起！）。

**Q: 一个人可以有多少个账户？**  
A: 无限多个。改变 account' 就能派生新账户，都由同一个助记词控制。

**Q: 不同币种能互相转账吗？**  
A: 不能。BTC 地址和 ETH 地址不兼容，硬币也存在不同的链上。

**Q: MetaMask 和 Ledger 生成的地址一样吗？**  
A: 一样。因为都遵循 BIP44，导入同一个助记词会生成相同的地址。
