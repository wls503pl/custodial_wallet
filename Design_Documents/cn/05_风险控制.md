# 交易所钱包系统风控设计指南

## 为什么需要风控？

想象一个交易所钱包就像一个银行。如果没有安全检查，坏人可能会：

- **偷走用户的币**（盗币）
- **虚假转账骗取资产**（欺诈）
- **用交易所洗黑钱**（洗钱）
- **员工内部作恶**（操纵数据）

风控系统就像一个"安全卫兵"，它的目标是在保护用户资产的同时，尽量不打扰正常用户。

---

## 架构升级：添加安全护栏

### 问题：原架构的风险

原来的系统让 wallet（钱包）和 scan（扫描）模块直接修改数据库。这就像让任何员工都能直接打开金库修改账本，太危险了！

### 解决方案：引入数据库网关

我们增加了一个"守门人"——**数据库网关（DB Gateway）**：

![数据库操作流程](../img/05_risk_control/read_write_process.png)

**流程说明：**

- **读取数据**：直接读数据库，保证效率
- **普通写入**：附带业务签名后，数据库网关验证通过才能写
- **敏感操作**：需要业务签名 + 风控签名的"双签"才能执行

---

## 数据库权限三个层级

就像医院里有不同的门禁权限：

| 权限等级  | 内容                    | 例子                   |
| --------- | ----------------------- | ---------------------- |
| 🟢 只读   | 直接查询，无需审批      | 查看区块、交易记录     |
| 🟡 普通写 | 需要业务签名            | 写入新交易数据         |
| 🔴 敏感写 | 需要业务签名 + 风控签名 | 用户提现、修改资金流水 |

关键敏感表包括：

- **withdraws**（提现表）
- **credits**（资金流水表）

---

## 完整的操作流程

### 普通操作（如存款）

```
钱包模块 → 数据库网关 → 数据库
          ↓
        验证业务签名
```

### 敏感操作（如提现）

```
钱包模块 → 风控系统 → 数据库网关 → 数据库
          ↓          ↓
       评估风险   验证双签
```

## 风控系统设计

### 核心规则

风控系统就像一个"守卫队长"，它遵循这些规则：

**1. 账户地址判定**

- 检查地址是否在黑名单中
- 检查是否被制裁或违规
- 如有异常立即冻结或拒绝

**2. 交易监控**

- 限制单笔提现金额（根据 KYC 等级调整）
- 限制每日提现频率
- 新设备/新地址短期内限制提现（防止"充币秒提"）
- 大额交易自动转人工审查

### 三张核心表

**风险地址表**

- 管理所有黑名单地址
- 快速判断是否高风险

**风控评估记录表**

- 记录每次评估的结果
- 保留审计痕迹
- 包含风险原因和建议

**人工审批记录表**

- 记录审核员的操作
- 记录审核结果和时间
- 用于后期复查和问责

## 签名机制：防止篡改和重放

### 为什么需要签名？

签名就像一份"带指纹的合同"，坏人无法伪造。

### 操作流程

![完整的提现安全流程](../img/05_risk_control/withdraw_riskControl.png)

**步骤详解：**

1. **钱包请求风控检查** → "这笔 100 元提现安全吗？"
2. **风控返回签名** → "我已评估，签上我的名"
3. **钱包添加业务签名** → "我也签名，双重认可"
4. **签名机验证并发起交易** → "检查无误，广播交易"

### 防重放攻击

假如坏人截获了一条"通过的签名"，能否重复使用？**不能！**

因为我们在签名中加入了：

- **operation_id**：每次操作的唯一编号（UUID）
- **timestamp**：操作时间戳

数据库网关维护一个"已使用签名表"，同一个 operation_id 只能用一次，其他尝试会被拒绝。

## 人工审查流程

当系统无法自动判断时，就轮到人来决策。

![人工审查流程](../img/05_risk_control/manual_review.png)

**流程说明：**

1. **审核员看到待审核提现** → 检查用户信息、交易细节
2. **作出决定（假设通过）** → 在系统中点击"通过"
3. **系统回调钱包** → 通知"审查通过，请继续"
4. **钱包继续提现流程** → 选热钱包、获取 Nonce、再次请求风控
5. **最终提现** → 业务签名 + 风控签名 → 发起交易

这个设计确保：

- ✅ 人工决策有记录可追踪
- ✅ 业务层能实时获知审核结果
- ✅ 不会重复审查同一笔提现

## 模块职责一览表

| 模块            | 职责                  | 权限                    |
| --------------- | --------------------- | ----------------------- |
| **wallet/scan** | 业务逻辑 + 业务签名   | 发起交易请求            |
| **风控**        | 风险评估 + 风控签名   | 评估风险等级，批准/拒绝 |
| **DB 网关**     | 数据库操作 + 双签验证 | 把关所有数据库写入      |
| **签名机**      | 交易签名 + 双签验证   | 生成最终交易签名        |

## 安全性提升总结

### 即使系统被攻击...

| 场景         | 防护措施                       | 结果    |
| ------------ | ------------------------------ | ------- |
| 钱包模块被黑 | 没有风控签名，无法执行敏感操作 | ✅ 安全 |
| 数据库被攻击 | DB 网关把关，验证所有写入      | ✅ 安全 |
| 签名被重放   | operation_id 防护，一次一用    | ✅ 安全 |
| 大额提现风险 | 转人工审查                     | ✅ 安全 |

### 性能与安全的平衡

```
普通数据查询 → 直接读数据库（快速）
              ↓
      敏感操作 → 双签验证（安全至上）
```

## 后续优化方向

- **智能风控规则**：根据历史数据自动调整风控参数
- **全链路审计**：记录每个操作点，支持完整追踪
- **异常检测**：用机器学习识别异常交易模式
- **异步通知**：用消息队列实现高效通知

---

## 总结

一个好的风控系统应该是：

- **安全第一** 🔒：多层防护，不给坏人机会
- **流程清晰** 📋：每一步都有记录和追踪
- **人机结合** 🤖：自动处理常规，人工审查复杂
- **用户友好** 😊：在保证安全前提下，尽量不打扰正常用户
