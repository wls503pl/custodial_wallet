# 处理用户充值

## 一、识别充值交易

### ETH 充值（原生代币）

用户直接转账到我们的钱包地址，交易结构很简单：

```
from: 用户地址
to: 我们的钱包地址  ← 关键！判断这个就行
amount: ETH数量
```

**识别方式**：检查交易的 `to` 地址是否是我们生成的用户地址。

**注意**：

- 如果用户通过合约转账，`to` 会是合约地址，无法识别。需要用 `debug_traceTransaction` 追踪内部调用（需要自建节点）
- 区块奖励无法识别（系统奖励，不是交易）

---

### ERC20 充值（代币）

用户通过调用 Token 合约的 `transfer()` 函数转账，流程更复杂：

```
from: 用户地址
to: ERC20合约地址  ← 不是用户！
input: transfer(用户地址, 金额)  ← 真实的转账在这里
```

**识别方式**：解析 `Transfer` 事件日志，而不是交易。

每笔 ERC20 转账会产生一个事件：

```
topics[0] = Transfer函数签名的哈希值
           = 0xddf252ad1be2c89b69c2b068fc378daa952ba7f163c4a11628f55a4df523b3ef

topics[1] = from地址（发送者）
topics[2] = to地址（接收者）  ← 匹配我们的用户地址
data = 转账金额
log.address = Token合约地址  ← 匹配我们支持的Token
```

**关键优化**：使用布隆过滤器（Bloom Filter）批量查询

```javascript
// 一次查询多个Token、多个用户
const logs = await getLogs({
  address: [USDT合约, USDC合约, DAI合约, ...],  // 所有Token
  topics: [
    transferTopic,  // 固定值
    null,           // 不过滤发送者
    [用户地址1, 用户地址2, ...]  // 过滤接收者
  ]
});
```

**风险防范**：

- 防止恶意 Token 虚假转账（要求开源+审计）
- Fee-on-transfer 代币会收手续费，需要用 `balanceOf()` 二次校验余额

## 二、处理区块分叉

### 什么是分叉？

区块链是分布式网络，有时会产生分叉：

- 一条分支被回滚
- 另一条分支成为主链
- 回滚分支上的交易也被撤销

### 两种处理方案

#### 方案 1：等待最终确定性（安全但慢）

只处理 `finalized`（最终确定）的区块，这些永远不会被回滚。

- **以太坊**：经过 2 个 epoch（约 6 分钟）后 finalized
- **Bitcoin**：追加 6 个区块后（约 1 小时）

缺点：用户要等很长时间才能看到充值成功。

#### 方案 2：实时处理 + 分叉回滚（业界标准）

实时处理交易，检测到分叉时自动回滚本地数据。

## 四、数据库设计

### 1. 区块表 (blocks)

记录扫描进度，用来检测分叉。

| 字段        | 说明                           |
| ----------- | ------------------------------ |
| hash        | 区块哈希（主键）               |
| parent_hash | 父区块哈希（用来检测分叉）     |
| number      | 区块号                         |
| timestamp   | 时间戳                         |
| status      | confirmed / orphaned（被重组） |

### 2. 交易表 (transactions)

记录识别到的充值交易。

| 字段       | 说明                                  |
| ---------- | ------------------------------------- |
| tx_hash    | 交易哈希（唯一）                      |
| block_hash | 所在区块                              |
| from_addr  | 发送者                                |
| to_addr    | 接收者                                |
| token_addr | Token 合约（ETH 为空）                |
| amount     | 金额（字符串存储，避免精度丢失）      |
| type       | deposit/withdraw/collect/rebalance    |
| status     | confirmed / safe / finalized / failed |

### 3. Token 表 (tokens)

全局记录所有支持的代币。

| 字段          | 说明                        |
| ------------- | --------------------------- |
| chain_type    | eth / polygon / bsc 等      |
| token_address | 合约地址（原生代币为 NULL） |
| token_symbol  | ETH / USDT / USDC           |
| decimals      | 小数位数（默认 18）         |
| is_native     | 是否原生代币                |
| status        | 0-禁用 / 1-启用             |

## 五、用户余额处理

### ❌ 方案 1：余额表（不推荐）

```
每笔交易 → 直接修改 balance 字段
```

问题：

- 无法对账，交易和余额对不上
- 交易重放 → 余额错乱
- finalized 交易回滚 → 无法处理

### ✅ 方案 2：流水表（推荐）

创建**资金流水表 (credits)**，每条记录对应一次资金变动：

| 字段         | 说明                                           |
| ------------ | ---------------------------------------------- |
| id           | 自增主键                                       |
| user_id      | 用户 ID                                        |
| amount       | 金额（正数入账，负数出账）                     |
| credit_type  | deposit / withdraw / trade_buy / trade_sell 等 |
| status       | pending / confirmed / finalized                |
| tx_hash      | 交易哈希                                       |
| reference_id | 关联业务 ID（保证幂等）                        |

关键约束：

```sql
UNIQUE(reference_id, reference_type, event_index)
```

保证交易不重放。

### 获取用户余额

创建聚合视图：

```sql
SELECT
  user_id,
  token_symbol,
  SUM(amount) as total_balance  -- 流水求和
FROM credits
WHERE status = 'finalized'
GROUP BY user_id, token_symbol
```

**优点**：

- ✅ 完整可审计，每笔账都能溯源
- ✅ 支持幂等性，避免重复
- ✅ 支持复杂业务（交易、内部转账等）
- ✅ 分叉回滚时，只需删除相关流水重新计算

## 七、关键要点总结

| 问题                  | 方案                                  |
| --------------------- | ------------------------------------- |
| 如何识别 ETH 充值？   | 检查 `to` 地址是否是用户地址          |
| 如何识别 ERC20 充值？ | 解析 `Transfer` 事件日志 + 布隆过滤器 |
| 如何处理分叉？        | 实时处理 + 分叉检测 + 数据库回滚      |
| 如何保证对账？        | 使用流水表 + 唯一性约束（幂等性）     |
| 如何高效查询余额？    | 聚合视图对流水求和                    |
| 如何避免重复？        | reference_id 去重 + 状态管理          |
